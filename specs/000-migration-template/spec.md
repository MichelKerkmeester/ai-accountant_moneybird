## 2. PROBLEM & PURPOSE

### Problem Statement
A Dutch sole trader keeps bookkeeping in Jortt and moves to Moneybird. The move touches real administration data, so an unplanned bulk change risks wrong ledgers, duplicate invoices or lost history. One large migration session also cannot be reviewed or interrupted safely.

### Purpose
This phase parent splits the migration into 23 ordered child phases (Phase 0 through Phase 22) with fixed rules, so each step is small, evidence-backed, reversible where possible and approved by the Operator before the next step starts. Source contract: [the source contract](../../sk-moneybird-accountant/references/migration/README.md) and [shared mechanisms](../../sk-moneybird-accountant/references/migration/shared-mechanisms.md).

> **Phase-parent note:** This spec.md is the ONLY authored document at the parent level. All detailed planning, task breakdowns, checklists, and decisions live in the child phase folders listed in the Phase Documentation Map below. This keeps the parent from drifting stale as phases execute and pivot.

## 3. SCOPE

### In Scope
- Phase 0 safety and system setup through Phase 22 cleanup, cancel or keep and archive, in order
- Jortt read-only. Every Jortt touch is a read that feeds an input list or a reconciliation
- Moneybird writes through moneybird-guard only, with the guard gate passed and Operator approval recorded before the write
- Migration records and evidence inside `migration-workspace/`, which stays git ignored, so no migration file enters version control
- One child folder per phase with its own spec, goal, plan, tasks, acceptance criteria and decision record

### Out of Scope
- The Jortt to Moneybird data conversion rules themselves. Each child phase references the matching section of [the source contract](../../sk-moneybird-accountant/references/migration/README.md)
- The shared mechanisms catalogue. It lives in [shared mechanisms](../../sk-moneybird-accountant/references/migration/shared-mechanisms.md) and is linked, not copied
- Repo level tooling changes to the skills that drive the phases

### Phase Transition Rules

- Each phase MUST pass `validate.sh` independently, with its exit gate recorded in `acceptance-criteria.md` and Operator approval recorded in `decision-record.md`, before the next phase begins
- Parent spec tracks aggregate progress via this map
- Use `/spec_kit:resume 000-migration-template/[NNN-phase]/` to resume a specific phase
- Run `validate.sh --recursive` on parent to validate all phases as integrated unit
- Phase 22 owns the cancel-or-keep decision and the archive verification. The archive is verified before the migration is called done

### Phase Handoff Criteria

| From | To | Criteria | Verification |
|------|-----|----------|--------------|
| Each phase | The next phase in order | Following the ordered list in [the source contract](../../sk-moneybird-accountant/references/migration/README.md), the phase exit gate passes, zero stop conditions stay open, and Operator approval is recorded | `acceptance-criteria.md` statuses in the child folder plus the `decision-record.md` entry |

## 4. REQUIREMENTS

- Every phase owns one child folder named `<phase + 1>-phase-<n>-<slug>/` under 000-migration-template and its own spec, goal, plan, tasks and acceptance criteria
- Jortt stays read-only in every phase. Reads are allowed as inputs. Any Jortt write is a stop condition
- Moneybird writes happen through moneybird-guard only, with the guard gate passed and Operator approval recorded
- Phase records and evidence stay in the git ignored `migration-workspace/`, outside version control
- Phases run in order. A phase that fails its entry check waits or rolls back. It does not push into the next phase
- No phase closes with an unresolved stop condition or an unrecorded Operator decision
